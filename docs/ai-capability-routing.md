# A2M — توجيه الأدوات المفضلة بواسطة AI Client

تاريخ المراجعة: 2026-11-05

## القرار المعماري

**فهم نية المستخدم واختيار الأداة المناسبة مسؤولية الـAI Client (مثل ChatGPT)، وليس A2M.**

- لا نبني قاموس مرادفات عربي/إنجليزي أو قواعد Regex متزايدة داخل Gateway.
- يوفّر A2M معلومات منظمة وموثوقة عن القدرات (المجال، الفائدة، الأولوية، التثبيت الحالي، الصحة، حالة الموافقة).
- يقرأ العميل هذه المعلومات، يطابقها دلالياً مع نية المستخدم، ثم يستدعي الأدوات المسجلة والمصرح بها.
- الأولوية **حسب نوع المهمة**، وليست إجباراً على تشغيل كل أدوات Premium في كل مرة.
- تعليمات Agent Skills مصادر غير موثوقة إلى أن يفحصها العميل؛ وهي لا تمنح صلاحيات إضافية ولا تبرر تجاوز سياسة MCP.

## القدرات المفضلة

| القدرة | دورها | سلوك الـAI client المتوقع |
| --- | --- | --- |
| OmniSkill | إنشاء، تحسين، تقييم وتعبئة Agent Skills | عند طلب Skill أو بنائها يستخدم تعريف `omni-skill` المكتشف وCLI الحالي: `route`, `init`, `validate`, `eval`, `package` وفق سياق المهمة |
| XERJ | فهم وفهرسة المشاريع والمستودعات | عند بدء العمل على مشروع: يفحص تشغيل Node والفهرس؛ يهيئ ويُفهرس المشروع المعتمد عند الحاجة، لا يعيد فهرسته كاملاً في كل رسالة |
| REA | Reverse Engineering | عند طلب هندسة عكسية لتطبيق/تجربة يختار REA، ويستخدم أدوات MCP المعتمدة فعلياً؛ لا يخلط «مكتشف» مع «مصرح بالتنفيذ» |

## واجهة الاكتشاف

`capabilities_list` يعرض `featured_capabilities` مرتبة ترتيباً ثابتاً لسهولة الاكتشاف، مع:
- `id`, `priority`, `description`, `use_for`, `suggested_use`
- `installed`, `executable`, `skill_id`, `status`, `mcp_available`

تُحل مسارات CLIs عند كل استعلام، من PATH أو مواقع مديري الحزم المعروفة. **هذا يعني استخدام التثبيت المحلي النشط وليس تثبيت نسخة أو pin تلقائي**. لا يعني اكتشاف أحدث إصدار متاح على الإنترنت، ولا استبدال إصدار المستخدم بغير إذنه.

لا توجد `capability_route(prompt)` مع قواعد لغوية داخل A2M؛ الـAI client هو من يختار الـcapability باستخدام فهمه للغة.

## القيود التشغيلية والأمان

1. اتصال ChatGPT قد يحتفظ بنسخة مخبأة من أسماء الأدوات؛ تجديد manifest أو إعادة ربط MCP قد يكون مطلوباً.
2. ملف موافقات `~/.a2m/mcp-approvals.json` هو حاجز صريح لتشغيل الـMCP الخارجي (موافقة لكل مزوّد وأداة). رؤية REA في `mcp_servers_list` لا تمنح حق تشغيله.
3. XERJ CLI وXERJ MCP وXERJ Node أجزاء مختلفة. تسجيل tools لا يثبت صحة الـnode، والفهرسة مسموحة داخل الـworkspace المعتمد فقط.
4. `AGENTS.md` إرشاد للـAI client الذي يقرأه؛ ليس ضماناً أن كل Host سيستخدمه أو سيستدعي `capabilities_list` تلقائياً.
5. خطأ الـYAML multiline في `description: >` تم التعامل معه كخطأ **استخراج بيانات** وليس كمشكلة فهم نية.
6. أي CLI يتطلب صلاحيات كتابة أو اتصالات خارجية يخضع لموافقة المستخدم وقيود البيئة؛ لا يُستخدم `start_process` لتجاوز منع مزوّد MCP.

## نتائج الفحص الحالية

- OmniSkill CLI مثبت، الإصدار الذي ظهر وقت الفحص `6.2.0`، واختبار `route` بطلب عربي أنتج DAG لإنشاء Skill.
- REA CLI مثبت، الإصدار الذي ظهر `6.8.0`، لكن REA MCP لم يكن مفعلاً من خلال A2M.
- XERJ CLI `1.0.0-rc.95`، واختبار Node معزول على منفذ مؤقت استجاب وأظهر 13 أداة MCP. الـNode المعتاد على المنفذ 9200 لم يكن نشطاً وقت الفحص.
- النسخة المعدلة من المصدر تحتاج بناء/نشر وإعادة تسجيل العميل عند الحاجة؛ الاختبارات المحلية وحدها لا تجعل التغييرات متاحة فوراً لاتصال ChatGPT الجاري.

## المتابعة التشغيلية المقترحة

- تهيئة تشغيل دائم وآمن للـXERJ Node، مع smoke test للبحث والفهرسة الفعلية في كل workspace معتمد.
- التحقق من REA MCP عبر `rea mcp doctor` واعتماد مجموعة الأدوات اللازمة فقط بعد مراجعة آثارها وصلاحياتها.
- اختبار OmniSkill end-to-end بإنشاء Skill تجريبية في مجلد مؤقت، وتشغيل validate/eval من نفس الإصدار النشط، والتحقق أن AI Client اختارها من وصف القدرة دون ذكرها في طلب المستخدم.
- بعد بناء نسخة Gateway وتحديث MCP manifest: اختبار ثلاث مهام مستخدم فعلية، والتأكد من اختيار الأدوات تلقائياً بناءً على المعنى، لا على التطابق النصي.
